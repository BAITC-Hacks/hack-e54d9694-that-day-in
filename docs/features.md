# Дополнительные функции: передача первому разработчику

Обновление 23.09.2026: ветка `codex/deploy` опубликована на
https://akim-five-hours.vercel.app; Redis подключён и проверен реальными публикациями.
Исправления совместимости и текущие ограничения описаны в [deployment.md](deployment.md).
Ниже сохранён исходный отчёт о подготовке функций до деплоя.

Ветка `codex/scenario-features`, PR #5, база `codex/resident-feedback` (PR #4).
Это серверная логика и контракты; вкладки, стили и клиентское состояние подключает первый разработчик.
Существующие `/api/catalog`, `/api/simulate`, `/api/analyze` и исходный JSON не изменены.
У каждого участника собственные 100 единиц. Общего расходуемого бюджета нет.

## Контракты и примеры

- `src/shared/features.ts`: Zod-схемы запросов и ответов, типы, версия дополнительных правил `1.0.0`.
- `src/shared/features-fixtures.ts`: явно тестовые примеры рейтинга, рекомендаций, события и презентации, без сети и секретов.
- Добавлены поля `evidence` для расшифровки ссылок в рекомендациях и слайдах; базовые контракты не менялись.
- `alternative-1`…`alternative-3` — локальные ID рекомендаций внутри ответа. Не переносить их между разными исходными сценариями.

Обычный сценарий во всех запросах:

```ts
const scenario = {
  dataset_version: catalog.dataset_version,
  decisions: [/* ровно 5 объектов { measure_id, district_id } */],
};
```

Цены, Score, эффекты и идентификатор участника клиент не передаёт. Лишние поля запрещены.
Новые POST-обработчики ограничивают JSON 32 КБ. Ошибки формата/правил — 422, устаревший dataset_version — 409, большой запрос — 413.

## Отдельная вкладка «Сравнение»

1. При открытии запросить `GET /api/leaderboard?offset=0&limit=20`.
2. По явной кнопке «Опубликовать результат» отправить `POST /api/leaderboard` с `{ ...scenario, display_name }`.
3. Обновить список через GET. Cookie отправляется автоматически при запросах к тому же домену.

POST возвращает `LeaderboardSubmitResponseSchema`: `{ policy: "personal_best", entry }`.
Сервер пересчитывает сценарий из своего каталога. В таблицу попадает **личный лучший результат**, а не последняя попытка.
При худшем или равном новом результате возвращается предыдущая запись, включая прежнее имя и дату.
Бюджет каждого участника независим. AI на место в рейтинге не влияет.

GET возвращает `LeaderboardResponseSchema`:

- `entries`: имя, ID, сценарий с районными результатами, дата, `rank`, `is_winner`;
- `best_score`, `winner_count`: лучший результат и число участников с ним;
- `total`, `offset`, `limit`: число участников и пагинация (limit 1–100);
- `current_participant_id`: подсветка собственной строки;
- `mode: "standard"`, `policy: "personal_best"`.

Места при равенстве: 1, 1, 3. Победителями считаются **все** участники с наибольшим Score, включая тех, кто на другой странице.
Сравниваются полные численные результаты, не округлённая подпись интерфейса.
Порядок внутри ничьей технический, он не определяет победителя.
Каждая версия датасета имеет отдельный рейтинг. События и проекции отзывов в стандартный рейтинг не включаются.

### Постоянное общее хранилище

Используется Redis через HTTPS REST (Upstash-совместимый), без новых npm-зависимостей.
Для публикации между устройствами нужно добавить в окружение серверного приложения:

```text
UPSTASH_REDIS_REST_URL=<HTTPS endpoint Redis>
UPSTASH_REDIS_REST_TOKEN=<server-only Redis token>
PARTICIPANT_SECRET=<случайный секрет не короче 32 символов>
```

Не использовать префикс `NEXT_PUBLIC_`. Один набор переменных для всех экземпляров сайта.
Ключи Redis: `akim:{standard-v1-<dataset_version>}:entries` и `:scores`.
Личный рекорд обновляется атомарным Lua-скриптом, чтение страницы также атомарно.
Одинаковые параллельные публикации не создают дубликат; поздний слабый результат не затирает сильный.
HTTP обращения к хранилищу имеют таймаут 5 секунд. Лимит — 10 000 участников на версию; существующие участники могут обновляться после достижения лимита.
Хранилище не имеет автоматического удаления записей; удаление/срок хранения — задача эксплуатации.
При отсутствии настроек/ошибке хранилища возвращается 503 `leaderboard_unavailable`, а не вымышленная пустая таблица.
Перед публичным запуском подключить ограничения частоты запросов на стороне хостинга.

Идентификация без аккаунтов: случайный UUID в подписанной HttpOnly SameSite=Lax cookie (Secure на HTTPS).
Имя — подпись, а не уникальный ключ. Очистка cookie или другой браузер создают нового участника.
Это рейтинг браузерных участников, не подтверждённых людей; для единого профиля на разных устройствах нужна отдельная авторизация.
GET при первом открытии выдаёт cookie: выполнить его до публикации. При смене PARTICIPANT_SECRET прежние cookie перестают проходить проверку.

## AI-рекомендации

`POST /api/recommendations` принимает обычный `scenario`.
Сервер перебирает все допустимые замены ровно одного решения, включая перенос районной меры.
Учитываются стоимость, пять разных мер, направления, несовместимости, лаги и синергии.
Возвращает до трёх вариантов с положительным приростом Score, отсортированных по приросту, затем стоимости.
Это локальный поиск, **не гарантия глобального оптимума**. Улучшение Score не гарантирует улучшения каждого района/показателя.

В ответе: `source`, `candidates` (removed/added/decisions/simulation/score_gain/cost_delta), `notes`, `evidence`, модель и версия промпта.
AI объясняет выигрыш и компромисс для каждого проверенного варианта. Не создаёт числовые результаты.
По кнопке «Применить» интерфейс заменяет весь массив решений на `candidate.decisions` и сбрасывает старый отчёт.
Перед этим убедиться, что текущий сценарий всё ещё соответствует `source.scenario_key` ответа.

- 200 `complete`: варианты и настоящее объяснение AI;
- 200 `no_improvement`: в пределах одной замены улучшений нет, AI не вызывается;
- 503 `ai_unavailable`: варианты остаются доступными, notes=null, причина в ai_error.

## Городские события и перераспределение

- `GET /api/events`: каталог синтетических учебных событий и event_version.
- `POST /api/events` с `{dataset_version}`: случайный выбор одного события по действию пользователя.
- `POST /api/events/simulate`: `{...scenario, event_version: "1.0.0", event_id}` — пересчёт выбранного/перераспределённого плана.

События: осадки, жара, сбой сервисов. Все эффекты и резервы заданы в `src/data/events.ts`.
Это новые игровые допущения, а не факты о городе или изменения authoritative dataset.
Событие происходит **перед внедрением** мер: меняет исходные показатели с ограничением 0–100 и резервирует 5 или 10 из личных 100 единиц.
После этого применяются существующие лаги и синергии на горизонте восьми кварталов.
Все меры ещё только запланированы, поэтому можно заменить их с полным возвратом цены. Частично выполненные проекты не моделируются.

Ответ содержит `simulation` от состояния после события, `total_budget` (initial/emergency_reserve/measures_spent/remaining),
`mode: "event_practice"`, `eligible_for_leaderboard: false`.
`simulation.budget.initial` — бюджет, доступный для мер после резерва (90/95), `total_budget.initial` всегда 100.
При превышении 422 нужно предложить пользователю изменить план; не показывать недопустимый Score.
Например, замена M5 на M4 в контрольном примере снижает стоимость мер 95 → 85, и план допустим при каждом событии.
Случайный выбор не влияет на обычную симуляцию; повторный расчёт выбранного event_id детерминирован.
Это тренировка: не сохраняется необратимый розыгрыш и допускается повторный выбор. Соревнование по событиям потребует отдельной общей сессии.

## Генерация краткой презентации

`POST /api/presentation`: `{...scenario, title?: string}`.
Сервер сам рассчитывает результат и получает настоящее AI-объяснение. Присланные клиентом отчёты/баллы не принимаются.
Ответ: `source`, `title`, `slides`, `markdown`, `evidence`, модель/промпт, статус.

При успешном AI получается 9 слайдов: обзор, мероприятия, бюджет, районы, Score, заключение, сильные стороны, риски, последствия.
Численные слайды всегда строятся из расчёта; текст AI отделён и имеет ссылки на факты.
При ошибке AI возвращаются 503 и 6 слайдов (5 расчётных + сообщение о недоступности).
Интерфейс может показать slides в своём дизайне или скачать markdown через Blob с MIME `text/markdown;charset=utf-8`.
Markdown экранирует заголовок и текст. Не вставлять сырые строки как HTML.
PPTX/PDF-оформление и визуальный просмотрщик не добавлялись: сейчас реализована логика и переносимое содержимое презентации.
